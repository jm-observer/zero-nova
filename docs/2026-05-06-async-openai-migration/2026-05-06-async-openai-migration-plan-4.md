# Plan 4: 前端回复区展示 Token 使用量

## Plan 编号与标题

Plan 4: 前端回复区展示 Token 使用量

## 前置依赖

Plan 2（OpenAiCompatClient 替换实现）

## 本次目标

1. 在前端每条 AI 回复内容下方展示本次请求的 token 使用情况
2. 展示字段至少包含：`prompt_tokens`、`completion_tokens`、`total_tokens`
3. 当本次响应未返回 usage 时，前端不展示该区域（避免展示错误或占位数据）
4. 保持现有消息渲染逻辑不变，仅做展示增强

## 涉及文件

| 文件 | 操作 |
|------|------|
| `crates/nova-agent/src/provider/types.rs` | 确认/补充 usage 字段在流事件中的透出能力 |
| `crates/nova-server/src/...`（网关消息转发相关文件） | 确认 usage 字段在协议层不丢失 |
| `frontend/...`（消息渲染组件） | 在回复下方新增 token 使用信息展示 |
| `schema/...`（若涉及共享类型） | 同步类型定义，确保前后端字段一致 |

## 详细设计

### 1. 数据来源与传递

- 使用 OpenAI 响应中的 `CompletionUsage` 作为来源。
- 后端统一映射为内部 `Usage`（`input_tokens` / `output_tokens` / `total_tokens`），并通过现有流式事件在最终完成事件中返回。
- 协议层仅透传，不新增与业务无关的包装层，避免前后端协议分叉。

### 2. 前端展示位置与样式

- 展示位置：每条 AI 回复气泡下方（同一消息卡片内）。
- 展示文案示例：`Tokens: prompt 123 · completion 456 · total 579`。
- 样式建议：弱化展示（较小字号、次级颜色），避免干扰主回复内容阅读。

### 3. 缺失数据处理

- `usage == None`：不渲染 token 行。
- 任一字段缺失：按 `0` 处理仅在后端已明确该语义时启用；默认建议保持“有则全显、无则不显”。
- 不在前端自行估算 token，避免与后端统计口径不一致。

### 4. 兼容性

- 对非 OpenAI provider：若后端能提供 `usage`，前端同样展示；否则保持不展示。
- 历史消息（无 usage 字段）保持兼容，不触发渲染异常。

## 测试案例

### 1. 正常路径

- 输入一条消息并收到 AI 回复，响应包含 usage。
- 断言前端在该条回复下展示三项 token 数据，且数值与后端一致。

### 2. 缺失 usage

- 构造不包含 usage 的回复事件。
- 断言前端不展示 token 行，页面无报错。

### 3. 多轮会话

- 连续发送多条消息。
- 断言每条回复仅展示各自的 usage，不串行、不复用上一条数据。

### 4. 回归验证

- 验证消息正文、Markdown 渲染、工具调用结果展示未受影响。
- 验证移动端与桌面端布局下，token 行不会导致消息卡片溢出或错位。
