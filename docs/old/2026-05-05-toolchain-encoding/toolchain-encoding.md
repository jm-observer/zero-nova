## 项目现状

1. 当前工具调用链中存在 stderr 解码失败问题，典型报错为 `Error reading stderr: stream did not contain valid UTF-8`。
2. 问题发生在“子进程输出编码”与“上层读取策略”不一致时，尤其在 Windows 场景下更容易触发（本地代码页与 UTF-8 不一致）。
3. 工具调用中存在跨 shell 嵌套（例如 Bash 中再调用 PowerShell）和复杂转义，增加了错误输出不可控的概率。
4. 工具参数在部分调用中存在 schema 外字段，导致执行器可能进入异常路径，放大链路不稳定性。
5. 当前错误处理对 stderr UTF-8 依赖过强，缺少“按字节保存 + 容错解码”的兜底能力。
6. 当前设计对 stdio 的关注不均衡，问题主要暴露在 stderr，但 stdout 与 stderr 采集策略尚未显式统一，存在行为不一致风险。
7. Linux 场景下虽然通常默认 UTF-8，但仍可能受 `LANG` / `LC_ALL`、容器基础镜像和 shell 差异影响，触发同类解码问题。

## 整体目标

1. 修复 stderr UTF-8 编码链路，确保跨平台调用下错误输出可稳定采集与展示。
2. 规范工具调用参数，严格约束为 schema 内字段，减少非预期执行路径。
3. 规范 shell 调用方式，消除不必要的跨 shell 嵌套，降低转义和编码复杂度。
4. 建立可回归验证的测试与观测点，防止同类问题反复出现。
5. 将 stdio（stdout/stderr）统一纳入编码与采集规范，避免只修 stderr 造成后续不一致。
6. 明确 Linux 场景的编码与 shell 行为基线，确保与 Windows 一致具备可诊断性。

## 风险与待定项

### 已知风险

1. 若仅在输出侧强制 UTF-8，而读取侧仍严格 `from_utf8`，仍可能在异常字节序列下失败。
2. 现网历史调用模板中可能已固化跨 shell 嵌套模式，改造后有兼容性风险。
3. 工具 schema 收紧后，旧调用请求可能被拒绝，需要给出明确错误信息和迁移指引。

### 待定项

1. stderr 原始字节是否需要持久化（仅内存返回，或落地到调试日志）。
2. 参数校验失败时策略：硬失败直接拒绝，还是先告警后自动裁剪无效字段。
3. 是否同步引入 stdout/stderr 长度上限与截断策略，避免极端输出导致内存压力。

## 建议实施顺序

1. 先完成 Plan 1，确保链路稳定可观测。
2. 再完成 Plan 2，减少异常输入来源。
3. 最后完成 Plan 3，统一调用策略并固化测试基线。
