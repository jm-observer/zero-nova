# nova-agent-lock-unification

## 时间
- 创建日期：2026-05-10
- 最后更新：2026-05-10

## 项目现状
`crates/nova-agent` 当前并发状态管理混用了 `std::sync::{RwLock, Mutex}` 与异步流程。主要问题：
- 在 `tokio` 异步调用链中存在同步锁读写，锁竞争时会阻塞运行时工作线程。
- 锁获取大量使用 `.unwrap()`，一旦 poison 或意外错误会触发 panic，不符合库层错误传播约束。
- 不同模块锁语义不一致（有的偏“状态快照读”，有的偏“短临界区写”），导致代码评审与后续维护成本高。
- 部分函数持锁范围偏大，包含序列化、路径计算、外部调用前置构建等，放大了竞争窗口。

## 整体目标
在不改变外部行为和协议的前提下，统一 `nova-agent` 的并发锁模型：
- 业务异步路径统一使用 `tokio::sync::RwLock`（必要时配合 `tokio::sync::Mutex`）。
- 消除生产代码中“锁相关 panic 风险点”，改为 `anyhow::Result` 传播并补充上下文。
- 收敛持锁范围，确保“读取-复制必要数据-释放锁-执行耗时逻辑”的固定模式。
- 建立可执行的锁使用约束与回归测试，防止后续回退到阻塞锁模式。

## 风险与待定项
- 风险 1：`std::sync` 到 `tokio::sync` 的 API 差异（`read()`/`write()` 需 `await`）会引发函数签名联动修改。
- 风险 2：若当前逻辑依赖“同步锁可在非 async 上下文使用”，迁移时需拆分调用层级。
- 风险 3：若持锁范围收缩不当，可能引入读写时序变化，需要补并发回归测试覆盖。
- 待定项：是否在本轮引入统一锁包装类型（例如 `SessionStateLock`），还是先完成直接替换后再抽象。
